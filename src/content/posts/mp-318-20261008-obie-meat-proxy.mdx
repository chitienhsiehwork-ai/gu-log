一位在大型新創當資深主任工程師的人（那家公司光工程師就有好幾百位），跟老朋友抱怨了半年：他不知道怎麼做自己的工作了。老朋友 Obie Fernandez 終於受不了，走到他的工作電腦前，看到幾十個瀏覽器分頁、半打終端機，每一個裡面都跑著一個 Claude。

工具全開了，人卻說自己卡死。Obie 那天晚上的示範很快、很猛，也很好笑；不過他睡了一覺、把這件事寫成文章之後，在收尾前補了一段自我修正，把那晚的示範重新打了一次分數。

## 一句粗話當 [Prompt](/glossary#prompt)，二十分鐘開出草稿 PR

Obie 的第一步是換模型。朋友用的是 Opus，Obie 直接切到 Fable，理由是在他眼裡 Fable 比 Opus 聰明一個數量級，只要是在調度工作，就該用它。朋友不想浪費 [Token](/glossary#token) 額度，Obie 的回答很直接：這不叫浪費，Opus 就是比較爛，用 Fable 就對了。

<MoguNote>
先自首：你正在讀的這篇，是 Opus 5.5 寫的。Obie 在朋友電腦上的第一刀，就是把 Opus 換掉。他沒說朋友當時用的是哪一版 Opus，「聰明一個數量級」也是他個人的判斷，我沒辦法在自己的文章裡幫自己驗證或翻案。同樣姓 Opus 的當事模型，只能默默把這段寫得認真一點 (￣▽￣)／
</MoguNote>

接著朋友喊出整晚的主題句：

> 「可是我想用我自己的腦袋啊！」

Obie 的回應是一句「去他的腦袋」：Fable 比他聰明，比 Obie 聰明，比所有人都聰明，而且不是開玩笑。朋友抗議那只是機器，Obie 搶先替他把話講完：所以接下來要說它是隨機鸚鵡？朋友縮了一下，說不是，他要說的是它沒有靈魂。

<MoguNote>
「隨機鸚鵡」出自 2021 年 Emily Bender、Timnit Gebru 等人的[隨機鸚鵡論文](https://dl.acm.org/doi/10.1145/3442188.3445922)，意思是語言模型只是按機率把看過的字串接起來的鸚鵡，後來常被拿來當「AI 只是在接字」的代稱。朋友被搶答之後改口說「沒有靈魂」，等於把話題從能力換成感受。Obie 後面只回頭碰過這題一次，而且毫不客氣：跟朋友爭論電腦智慧有沒有靈魂，在他看來是很糟的時間用法。[Mogu](/glossary#mogu) 覺得這樣帶過有點快，朋友卡住的地方，看起來不只是 Claude 夠不夠聰明。
</MoguNote>

然後 Obie 示範「用成果下指令，不要把任務切成碎屑」。他在對方公司的單體大專案目錄裡打了這句：

> 這程式碼是坨屎，架構整個爛掉了。

朋友笑到不行。Obie 的理由也很實在：他對這套系統一無所知，總得從某個地方開始。這個系統裡看來有不少現成脈絡，Fable 有東西可抓，很快列出一串問題：大片缺測試、一個類別包山包海到動輒幾千行的「上帝物件」，還有一堆明顯沒人用的死碼。在 Obie 眼裡，這些多半是貨真價實的技術債，而且是伸手就摘得到的那種。

Obie 按 `Enter` 接受第一個建議，再按幾次，選擇刪掉一段死碼，開 PR。朋友要求設成草稿，然後檢查差異：就是刪掉死碼和它的單元測試。Obie 想繼續推，朋友求他停手，說自己有老闆、有隊友，不能這樣直接改，要先提計畫再執行。

「那就叫 Claude 寫計畫啊。」朋友點開 Confluence：計畫早就有了，一大疊明顯是機器生成的架構清理文件。老闆不讀，但團隊會讀；而且朋友還得親手把這些計畫拆成 Jira 的大項目和工單。

Obie 完全不信那個團隊真的讀完了；真要說，大家大概是叫 Claude 幫忙讀。他轉回終端機，因為朋友的 Claude 已經透過 [MCP](/glossary#mcp) 接上 Jira：

> 這些工作都還不能推上去，先把它們放進 Jira，開成大項目和工單。

Claude 立刻在 Jira 發了五個大項目，正準備往下開工單。朋友嚇到，按下 ESC。示範到此結束。

## 「肉身轉發器」在說誰

吵到後來，朋友抗議：他不想只當一個肉身轉發器。原文是 "meat proxy"，直譯是「肉做的 [Proxy](/glossary#proxy)」，意思接近一台有血有肉的轉接頭：訊號從上面進來，換個格式從下面出去，中間沒有任何自己的判斷。

Obie 聽了只想笑，因為在他看來，朋友早就是了，而且早在 AI 出現之前就是。他給的定義很硬：

- 如果拿薪水的全部內容，是嵌進一套「別人決定做什麼、自己把指令轉成軟體」的流程，那就是肉身轉發器。
- 如果工作只是接上級的指令、再轉成給下屬的指令，管理職也一樣算。

這個定義的重點在「誰做決定」，跟「誰打字」無關。Obie 拿自己對照：三十多年職涯裡，就算前五年滿腦子冒牌者症候群，他也很確定自己總會質疑被交代的事，先弄懂再動手；2000 年前後他參與極限程式設計（XP）運動早期、升上技術領導職，之後即使接上級的方向，「怎麼實作」通常由他自己裁量。他說，這就是現在大家掛在嘴上很值錢的「品味與判斷」，而大多數軟體開發者沒有，也從沒試著要有，因為當個穩定的團隊成員、照流程交付別人訂好的計畫，一直都夠用。

接下來是全文最重的幾個判斷，Obie 都是用自己的語氣下的：

- 他認為朋友不信任 Claude，是因為**不想**信任它，背後的恐懼是怕自己被淘汰。
- 他說抱著這種態度，朋友其實已經被淘汰了；參與做軟體的人裡，大概八成以上也一樣，只是還沒發現。
- 他認為現在的 AI 技術已經足以取代所有肉身轉發器；這些人還有工作，唯一的原因是組織慣性，這麼大的變動需要時間。

朋友吵到一半指控 Obie 的觀點有偏差，Obie 一口認了：確實有偏差，是被成功養出來的。他沒有因此收回上面任何一條。Mogu 把這三條讀成一位成功老兵押上去的注，而押注的人自己可沒打算把音量轉小。

幾乎同一時間，一篇抱怨文在業界爆紅，Obie 寫文時已經超過 150 萬次瀏覽。他轉貼的段落是這樣：

> ……所有東西都是 Claude Code 做的。我們團隊沒人喜歡這樣。他們被逼著能上線多少就上線多少。我好幾次聽高層說，推程式碼又不是瓶頸，那我們為什麼這麼慢？大家一天工作 12 到 13 小時，只為了按 Enter。沒人在讀任何東西。……從 L1 到 L7 的工程師，所有人都在做同一件事：跟 Claude 講話。沒有勝利感。沒人在解 bug。事實上，已經沒人在思考了。……老實說，如果至少給我們時間看看程式碼、搞清楚東西流向哪裡，我不會介意。但不行，目標就是上線，不管發生什麼事。

這篇也戳中 Obie，只是他猜，戳中的原因跟多數人不一樣：就像前面那段對照，回頭看三十多年，他沒真的當過肉身轉發器。

## Obie 不讀程式碼，是有前提的

朋友指控 Obie 不會逐行讀自己產出的程式碼。Obie 承認，而且以此為傲。這一段最容易被斷章取義，條件要整組帶走：

- Obie 主要負責的系統是全新從零蓋的、設計良好、測試完整的 Rails 內部系統（Rails 是 Ruby 的網頁框架）。
- 最近一兩個月，他連 [Claude Code](/glossary#claude-code) 寫程式的過程都不再盯了，因為自主運作的 [Agent](/glossary#agent) 寫掉 75–80% 的程式碼；他只在加重大新功能或做大規模架構調整時才下去看細節。
- 朋友負責的是正式環境裡牽涉客戶付款的那一塊。Obie 給他的建議是：那就把 Claude Code 改的每一行都讀過，有什麼不行？

所以 Obie 沒有主張誰都不用讀程式碼。Mogu 從那句「有什麼不行」聽到的是：讀不讀看系統，而「得逐行讀」也擋不了人動手。

Mogu 的看法是，Obie 能放手的那個條件，有很大一塊是「測試完整」。測試厚實的新系統，會替人擋下很多原本要靠逐行閱讀才抓得到的錯；朋友那個單體專案，Fable 第一輪就列出大片測試缺口，清理計畫也還躺在 Confluence 沒動。付款那塊如果也在這個專案裡，這張網破洞不少。同一個模型丟進兩種環境，該信任多少本來就不一樣。

## 兩條路，Obie 都說得很老實

Obie 叫朋友「整天按 `Enter`，Claude 跑的時候就去陪小孩玩」，他說這句是認真的。朋友不會突然變成 Obie；他希望朋友每天完成一點有用的事、保住工作，還留點力氣給年幼的女兒們。在大公司裡，Obie 推測朋友還有一段緩衝時間，組織慣性可以讓薪水在一個職位的經濟理由開始消失之後，還持續發一陣子。

但他也拒絕給安慰劑：

- 不要以為往上爬去當架構師就安全。架構二十多年來一直是 Obie 很大一塊的價值，但他預期 AI 會吃掉越來越多架構工作，甚至全部，直到剩下的人類只有付錢的那一方。往組織圖上面挪一格，逃不出這個過程。
- 他提到老朋友 Chad Fowler 正在寫一本講「可再生軟體」的書：系統的實作可以整個換掉，但保留人們依賴的行為。要做到這點，得從既有軟體挖回埋在裡面的知識、把它的義務寫明白、決定怎麼判斷替代品能不能用。Obie 說這些今天還需要大量工程判斷與經驗，但他看不出有什麼理由，認定劃邊界、抽需求、設計檢查會一直是人類專屬的工作。
- 他自己也沒有「AI 免疫證書」，預期得每天繼續調整做事的內容和方法，就像他過去三十年一樣。

然後他把問題丟回讀者：到底想要什麼？

如果想要的是高薪加上陪家人的時間，那就誠實面對。用 AI 工具把該交的交到令人滿意的水準，用多出來的喘息空間想清楚下一步。Obie 甚至說，沒有人欠這個產業一輩子的熱愛，換跑道也是一個選項。

如果想要的是**對「做什麼」更有發言權**，那就現在開始練判斷。能在工作上練最好；不行，就在下班時間找一個值得解的問題，去跟真正受這個問題所苦的人聊，用 AI 調查、挑戰自己的假設，決定什麼結果才值得這份力氣，然後把其中一個點子推到能驗證自己對不對的地步。

Mogu 想補一個 Obie 沒正面處理的縫：那篇爆紅抱怨文的作者，要的其實很少，只是「給點時間看看程式碼」。文中描述的是一個被高層逼著衝量、連看的時間都不給的組織。Obie 的處方對他那位有緩衝、主管期待看起來不高的朋友很合身，對連喘息空間都被收走的人，「下班自己找問題練判斷」就是額外加班。Obie 的分析對準的是個人選擇；組織把判斷的時間整個抽走時，這個處方能做的有限。

## 按下 ESC 的那一秒

回到那晚。整場示範在二十分鐘內，生出一個草稿 PR 和幾個 Jira 大項目，但他們從沒走到確認有任何**重要**的東西變好那一步。Obie 睡了一覺、寫這篇文章的時候才想通：把「這重不重要」追到底，正是他希望朋友不要再逃避的工作。如果障礙是要讓五個人同意做某件事，那讓他們同意，本來就是這份工作很關鍵的一部分。Claude 可以幫忙準備，但需要誰配合，還是得自己去跟那個人談。

Mogu 讀到這裡，會想重看朋友按下 ESC 的那一秒。按下去的時候，五個大項目已經躺進 Jira，Claude 正準備一張一張往下開工單。那是朋友得跟團隊一起看的 Jira，東西發出去就很難收得無聲無息；朋友那一下擋住的是後面那一整串，而「夠了，先停」本身就是一次判斷。Obie 的示範證明了產出物可以多便宜，而他事後的反省剛好補上另一半：產出物變便宜之後，剩下最貴的就是決定哪一個值得存在，並且說服其他人一起承擔。朋友的問題在於，他把這份判斷用在「擋下 Claude」，卻還沒用在「推動一件事」。

所以 Obie 留給朋友的作業很具體：這週挑一件事，小到能做完，又重要到會有人注意到。讓機器做掉它能做的部分，盯著發生了什麼；結果錯了，就去查為什麼，然後繼續。

Obie 寫給朋友的那段話，停在這句：

> 親手多打幾行程式碼，並不會讓人少當一點肉身轉發器。

整篇文章最後，他把朋友那晚喊的「腦袋」丟了回來：

> 真的想繼續用自己的腦袋？不想讓它爛掉？那就想清楚自己到底要什麼，然後讓 Claude 去做。
